# 对于几个基础概念的阐述&底层原理的细究

分析来自 Gemini 3.1 Pro

## Skill & MCP

在 AI Agent 的开发中，**Skill（技能/工具）** 和 **MCP（Model Context Protocol，模型上下文协议）** 是两个紧密相关但处于不同层面的概念。

简单来说：**Skill 是 Agent 能够执行的具体“动作”，而 MCP 则是目前为了更高效地管理和接入这些动作而诞生的“通用标准接口”。**

下面为您详细拆解这两个概念：

---

### 一、 SKILL (技能 / 工具)

大模型本身被困在服务器里，且知识只停留在它训练截止的那一天。Skill 就是打破这个限制的**“手和脚”**以及**“感官”**。

#### 1. 核心本质：Function Calling（函数调用）

Skill 的底层技术其实就是 Function Calling。开发者向大模型提供一段关于某个函数的描述（包含函数名、功能说明、需要传入的参数类型等）。
当用户下达指令时，大模型不会直接回答文本，而是**输出一段结构化数据（通常是 JSON）**，告诉开发者：“请帮我执行 A 函数，并且带入 B 和 C 这两个参数。”

#### 2. Skill 的常见类型

**信息获取类（“眼睛”）：** 联网搜索（Google Search API）、查询实时天气、读取本地 PDF 文件、查询公司内部的数据库。
**动作执行类（“手脚”）：** 发送邮件、在 Jira 里创建一个任务、操作智能家居（如关灯）、执行一段 Python 代码。

#### 3. 传统 Skill 开发的痛点

在没有统一标准之前，如果要在 Agent 里加一个“查天气”的 Skill，开发者需要写一堆胶水代码：接入天气 API、处理鉴权、把数据转换成大模型能懂的格式……如果要接入 10 个工具，就要写 10 遍不同的对接代码；如果换了一个不同的大模型（比如从 GPT-4 换成 Claude），可能还得修改接口逻辑。

---

### 二、 MCP (Model Context Protocol 模型上下文协议)

为了解决上面提到的“各自为战”的痛点，Anthropic（开发 Claude 的公司）主导推出了 **MCP**。

#### 1. 通俗理解：AI 界的“Type-C 接口”或“USB 协议”

以前给手机充电，苹果要 Lightning，安卓要 Micro-USB。现在统一成了 Type-C。
MCP 就是 AI Agent 与外部世界（数据源、工具）连接的**统一标准协议**。只要你的工具符合 MCP 标准，任何支持 MCP 的 Agent（无论是 Cursor、Claude Desktop 还是你自己开发的 Agent）都可以“即插即用”地调用它。

#### 2. MCP 的核心架构

MCP 采用了类似于“客户端-服务端（Client-Server）”的架构：
**MCP Host / Client（宿主/客户端）：** 就是你的 AI Agent 或 AI 应用（比如你的聊天机器人）。
**MCP Server（服务端）：** 这是一个独立的轻量级程序，专门负责包装工具和数据。比如你可以运行一个“GitHub MCP Server”或“Postgres 数据库 MCP Server”。

#### 3. MCP 到底提供了什么？

一个标准的 MCP Server 可以向 Agent 提供三种东西：
**Resources (资源)：** 静态数据。比如直接把本地的一个日志文件或者一段代码喂给大模型作为上下文。
**Tools (工具/即 Skill)：** 允许 Agent 执行动作（比如调用 API、执行脚本）。这就是上面提到的 Skill。
**Prompts (提示词模板)：** 提供预设好的指令模板，方便 Agent 快速进入特定任务状态。

#### 4. 为什么 MCP 是颠覆性的？

**解耦：** 你的 Agent 核心逻辑 和 外部工具代码 完全分开了。
**生态复用（N x M 变成 N + M）：** 以前 3 种 Agent 接入 5 种工具，要写 15 次对接代码。现在，5 种工具只要写 5 个 MCP Server，任何支持 MCP 的 Agent 都可以直接连上去用。社区现在已经有海量现成的 MCP Server（比如飞书 MCP、Notion MCP、MySQL MCP 等），开发者直接拉下来就能让自己的 Agent 具备这些能力。

---

### 总结：两者的关系

**Skill** 强调的是 **“能力本身”**（比如能发邮件、能查数据）。
**MCP** 强调的是 **“能力的接入方式”**（用标准化的协议把 Skill 喂给 Agent）。

在现代的 Agent 架构中，最优雅的实践就是：**将所有的外部 Skill 封装成一个个独立的 MCP Server，然后让你的 Agent 作为 MCP Client 去连接它们。** 这样不仅代码整洁，而且未来的扩展性会极强。

## Function Calling

**Function Calling（函数调用）**是真正让大模型“长出手脚”的魔法，也是绝大多数 AI Agent 实现 Skill（技能）的底层技术。

要彻底弄懂它，首先要纠正一个常见的误区：**大模型本身并不能直接运行任何代码。**

大模型就像一个被锁在房间里的“绝顶聪明的瞎子”，他上知天文下知地理，但没法上网，也不会点外卖。**Function Calling 的本质，是建立了一套大模型与外部程序沟通的“黑话”。**

下面我用一个非常生活化的例子，详细拆解这个过程。

---

### 一个通俗的比喻

假设大模型是**老板**（坐在办公室，只会说话），你（开发者）是**秘书**（坐在外面，有电脑能上网，能执行指令）。

**没有 Function Calling 时：** 客户问老板“北京今天天气怎么样？”老板因为没法上网（只有过去的知识），只能胡编乱造，或者回答“我不知道”。
**有 Function Calling 时：** 你给老板递了一张“工具清单”，上面写着：“老板，如果你想查天气，请填写这张《查天气申请表》，填好城市名，递给我，我去查。” 老板收到问题后，填好表递交给你，你查完后把结果告诉老板，老板再润色成漂亮的话回复客户。

---

### Function Calling 的标准工作流（附“查天气”的例子）

假设用户对大模型说：**“帮我看看今天北京的天气怎么样，我要不要带伞？”**

完整的 Function Calling 流程分为以下 5 步：

#### 第 1 步：你（开发者）把工具清单告诉大模型

在开始对话时，除了系统提示词，你还要传给大模型一段 JSON 格式的“工具描述”。
也就是告诉它：你有一个叫 `get_weather` 的函数，需要传入 `location`（城市）这个参数。

```json
// 传给大模型的工具描述
{
  "name": "get_weather",
  "description": "获取指定城市的当前天气情况",
  "parameters": {
    "type": "object",
    "properties": {
      "location": {
        "type": "string",
        "description": "城市名称，例如：北京、上海"
      }
    },
    "required": ["location"]
  }
}
```

#### 第 2 步：大模型进行推理，决定调用工具

大模型收到用户的请求（“北京今天天气...”）和你的工具清单后，它心里一盘算：“这个问题靠我脑子里的历史知识答不出来，但我发现 `get_weather` 这个工具刚好能用上。”

于是，大模型**停止生成普通的文本对话**，转而输出一段特定格式的 JSON 数据，要求调用这个函数。

```json
// 大模型的输出（它没有直接回答用户，而是输出这段指令）
{
  "function_call": {
    "name": "get_weather",
    "arguments": "{\"location\": \"北京\"}"
  }
}
```

#### 第 3 步：你（开发者）在本地执行真正的代码

你的系统拦截到了大模型的这段输出。系统发现：“哦，大模型想让我去查北京的天气！”
于是，**你的代码（而不是大模型）**接管了工作。你的代码调用了真实的天气 API（比如去调取气象局的接口），并得到了真实的返回数据：

```json
// 你代码调用真实天气API得到的结果
{
  "temperature": "22℃",
  "condition": "中雨",
  "wind": "微风"
}
```

#### 第 4 步：你把结果“喂”回给大模型

你拿到数据后，把这个结果作为一个新的消息，再次发给大模型。
相当于秘书跑进办公室对老板说：“老板，我查过了，API返回的原始数据是 22℃，中雨。”

#### 第 5 步：大模型生成最终的自然语言回答

大模型收到真实的天气数据后，结合用户一开始的问题（“我要不要带伞？”），最终生成了一段贴心的话语反馈给用户：

**大模型最终输出给用户的内容：**
> “今天北京的气温是22℃，目前正在下中雨哦。建议您出门时务必带上雨伞，注意保暖！”

---

### 总结

理解 Function Calling，记住这三句话就够了：

1. **开发者定义函数，大模型理解函数。**（提供说明书）
2. **大模型不执行函数，大模型只输出参数。**（填申请表）
3. **开发者执行函数，把结果交还给大模型做总结。**（秘书跑腿，老板汇报）

这就是 AI Agent 中 Skill 的最底层运作逻辑。所有的工具（联网搜索、操作数据库、发邮件）都是建立在这个一来一回的机制之上的。
