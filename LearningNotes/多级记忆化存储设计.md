# Agent 多级记忆化存储设计

> **Session 时间**: 2026-03-20
> **讨论主题**: Agent 系统的多级记忆架构设计与实践

## 背景

在 AI Agent 系统中，如何有效管理对话上下文和长期知识是核心问题。本次讨论基于 **EfficiencyPlatform** 项目（Spring AI + PostgreSQL + PGVector），对比分析了不同的多级记忆架构方案。

---

## 三种架构方案对比

### 方案一：当前项目架构（双层）

```java
┌─────────────────────────────────────────────────────────┐
│  L1: 内存窗口（MessageWindowChatMemory）                 │
│  ├─ 存储：JVM 内存                                       │
│  ├─ 内容：最近 N 条完整对话                              │
│  ├─ 配置：maxMessages 可调整                            │
│  └─ 作用：保持短期对话连贯性                             │
└─────────────────────────────────────────────────────────┘
                        ↓
┌─────────────────────────────────────────────────────────┐
│  L2: 向量知识库（PostgreSQL + PGVector）                 │
│  ├─ 存储：持久化数据库                                   │
│  ├─ 内容：Embedding 向量（维度1536）                     │
│  ├─ 检索：语义相似度搜索（TopK + Filter）                │
│  └─ 作用：长期知识检索（RAG）                            │
└─────────────────────────────────────────────────────────┘
```

**实现细节**：

```java
// L1: 短期记忆
new PromptChatMemoryAdvisor(MessageWindowChatMemory.builder()
    .maxMessages(chatMemory.getMaxMessages())
    .build());

// L2: 长期记忆（向量检索）
SearchRequest searchRequest = SearchRequest.builder()
    .query(message)
    .topK(5)
    .filterExpression("knowledge == '" + tag + "'")
    .build();
List<Document> documents = vectorStore.similaritySearch(searchRequest);
```

**优点**：

- 架构简单，易于维护
- Spring AI 原生支持
- 向量检索准确度高

**缺点**：

- 重启后 L1 清空，丢失上下文
- 超出窗口的对话无法恢复
- 缺少审计和历史追溯能力

### 方案二：同学提出的三层架构（初版）

```java
┌─────────────────────────────────────────────────────────┐
│  L1: 内存详细窗口（最近10-20条完整对话）                  │
└─────────────────────────────────────────────────────────┘
                        ↓
┌─────────────────────────────────────────────────────────┐
│  L2: 内存长期记忆总结（AI 压缩的历史摘要）                │
│  └─ 例如："之前讨论了数据库优化，建议添加索引"            │
└─────────────────────────────────────────────────────────┘
                        ↓
┌─────────────────────────────────────────────────────────┐
│  L3: 磁盘持久化                                          │
│  ├─ MongoDB：所有聊天总结（全写）                        │
│  └─ 向量数据库：AI 筛选的有价值知识（选择性写）           │
└─────────────────────────────────────────────────────────┘
```

**关键机制**：

- **L1→L2 触发**：窗口满时，AI 总结最老的消息
- **L2→L3 触发**：会话结束/定时任务
- **AI 筛选逻辑**：过滤"嗯啊哦"等助词，只存有效内容

**优点**：

- 解决长对话上下文丢失问题
- 自动积累知识，无需手动导入
- 存储分层，节省成本

**问题分析**：

#### 问题1：复杂度高

需要实现多个触发逻辑：

- L1→L2 的总结时机判断
- 总结算法的质量保证
- MongoDB + 向量库的双写一致性
- AI 筛选的准确性验证

#### 问题2：总结压缩丢失细节

```java
原始对话：
"我的 MySQL user 表有字段 id, name, email，现在100万条数据查询很慢"
"建议在 email 字段加索引：CREATE INDEX idx_email ON user(email)"

AI 总结后：
"讨论了数据库性能，建议添加索引"

丢失：表名、字段名、具体SQL、数据量
```

#### 问题3：LLM 判断"有价值"不可靠

```python
对话: "我司内部加密算法是 AES-256"
→ LLM 判断：有价值，写入向量库
→ 风险：敏感信息泄露 ❌

对话: "Bug 修复：第327行加了 null 检查"
→ LLM 判断：无价值
→ 实际：未来类似 bug 很有参考价值 ❌
```

#### 问题4：MongoDB 存总结的必要性存疑

- 总结已丢失细节，审计时看不到原始对话
- 如果要存完整对话，总结就是冗余数据
- MongoDB 不支持向量检索，只能全文搜索

#### 问题5：内存 L2 层重启后清空

```java
重启前（内存）：L1 + L2 = 总结 + 最近20条
重启后：L1 + L2 = 空 🚨
从向量库检索：只能拿到"相似片段"，不是"完整连续上下文"
```

### 方案三：同学的优化方案（终版）

基于反馈，同学澄清了设计细节：

```java
┌──────────────────────────────────────────────────┐
│ L1+L2: ConversationSummaryBufferMemory (内存)    │
│ ├─ 最近N条：完整消息                              │
│ └─ 超出N条：AI 总结压缩                           │
│    例如：20条对话 → 总结成3句话                   │
└──────────────────────────────────────────────────┘
         ↓ 实时筛选，异步写入
┌──────────────────────────────────────────────────┐
│ L3-A: 向量数据库（核心长期记忆）                  │
│ ├─ AI 筛选：过滤"嗯啊哦"等无效内容                 │
│ ├─ 存储：embedding 向量                           │
│ └─ 恢复：重启后根据 user_id + metadata 检索      │
└──────────────────────────────────────────────────┘
         ↓ (可选) 仅用于前端展示
┌──────────────────────────────────────────────────┐
│ L3-B: MongoDB（非核心，可不要）                   │
│ └─ 用途：前端展示历史对话                         │
└──────────────────────────────────────────────────┘
```

**核心改进**：

1. **L1+L2 合并**：使用 `ConversationSummaryBufferMemory` 一体化处理
2. **MongoDB 降级**：仅作为前端展示层（非必需）
3. **AI 筛选目的明确**：防止助词干扰向量检索，而非判断"有价值"

**ConversationSummaryBufferMemory 原理**：

```python
# LangChain 实现逻辑（伪代码）
class ConversationSummaryBufferMemory:
    def __init__(self, max_token_limit=2000):
        self.buffer = []      # 最近的完整消息
        self.summary = ""     # 历史总结

    def add_message(self, message):
        self.buffer.append(message)

        if token_count(self.buffer) > max_token_limit:
            # 总结最老的消息，释放空间
            old_messages = self.buffer[:5]
            self.summary += llm.summarize(old_messages)
            self.buffer = self.buffer[5:]

    def get_context(self):
        return self.summary + "\n".join(self.buffer)
```

**优点**：

- 自动平衡完整性和容量
- 近期保持细节，远期压缩存储
- LangChain 生态成熟方案

**仍存在的问题**：

#### 问题1：重启后 L1+L2 清空

```java
重启前内存：总结 + 最近20条完整消息
重启后：空
解决方案：必须有持久化层（MySQL/MongoDB）用于恢复
```

#### 问题2：向量检索无法精确恢复上下文

```java
// 期望：按时间顺序查询
vectorStore.findByUserId(123).orderByTime()  // ❌ 做不到

// 实际：按相似度排序
vectorStore.similaritySearch(query, filter="user_id==123", topK=5)
// 返回 [相似度0.88, 0.85, 0.60]，不是时间顺序
```

**场景问题**：

```java
向量库存储：
1. "讨论了用户注册功能" (相似度: 0.85)
2. "讨论了订单支付流程" (相似度: 0.60)
3. "讨论了用户登录逻辑" (相似度: 0.88)

用户问："继续之前的注册功能"
检索结果顺序：[3, 1, 2] ← 按相似度，不是时间
问题：可能先返回"登录逻辑"而非"注册功能"
```

#### 问题3：AI 筛选增加延迟和成本

```java
每轮对话流程：
用户消息 → ChatModel.call() → 助手回复
           ↓
       再调用一次 LLM ← 增加延迟 0.5-2秒
           ↓
     判断是否写向量库

成本分析：
假设每天 1000 轮对话
- 正常：1000 次 LLM 调用
- 加筛选：2000 次 LLM 调用（翻倍）
- 额外成本：$10-50/天
```

#### 问题4：Spring AI 不支持 ConversationSummaryBufferMemory

```java
// Spring AI 只有：
- InMemoryChatMemory
- MessageWindowChatMemory

// ConversationSummaryBufferMemory 是 LangChain 概念
// 需要：
// 1. 迁移到 LangChain4j（但也没有此功能）
// 2. 或自己实现（增加开发成本）
```

#### 问题5：总结压缩必然丢失细节

```java
原始（10轮对话）：
👤 "MySQL user 表字段：id, name, email, phone"
🤖 "收到，5个字段"
👤 "user 表100万数据，查询慢"
🤖 "建议在 email 加索引"
👤 "SQL 怎么写？"
🤖 "CREATE INDEX idx_email ON user(email)"

AI 总结后：
"讨论了 user 表性能优化，建议添加索引"

丢失：
- 具体字段名 (email)
- 具体 SQL 语句
- 数据量（100万）

后果：
10轮后用户问："刚才那个 SQL 再写一遍"
AI 看到的上下文："讨论了性能优化"
AI 回答："抱歉我不记得具体 SQL 了" 🚨
```

## 推荐方案：三层混合架构

综合以上分析，推荐以下架构：

```java
┌─────────────────────────────────────────────────┐
│ L1: MessageWindowChatMemory (内存)              │
│ └─ 最近20条完整消息（Spring AI 原生支持）        │
└─────────────────────────────────────────────────┘
         ↓ 每轮对话后异步写入
┌─────────────────────────────────────────────────┐
│ L2: MySQL (持久化对话历史)                       │
│ ├─ 表: chat_history                             │
│ ├─ 字段: conversation_id, user_id, message,     │
│ │        role, created_at                       │
│ └─ 用途:                                         │
│     ├─ 重启后恢复 L1                             │
│     ├─ 前端展示历史对话                          │
│     ├─ 审计和分析                                │
│     └─ 按时间精确查询                            │
└─────────────────────────────────────────────────┘
         ↓ 会话结束后批量筛选
┌─────────────────────────────────────────────────┐
│ L3: PostgreSQL + PGVector (长期知识)             │
│ ├─ 筛选策略:                                     │
│ │   ├─ 规则过滤（长度、语气词）                  │
│ │   └─ LLM 批量筛选（凌晨异步）                   │
│ └─ 写入时机:                                     │
│     ├─ 每个会话结束后                            │
│     └─ 或管理员手动标记                          │
└─────────────────────────────────────────────────┘
```

## 实现代码

### 数据库表结构

```sql
-- 对话历史表
CREATE TABLE chat_history (
    id BIGINT PRIMARY KEY AUTO_INCREMENT,
    conversation_id VARCHAR(64) NOT NULL COMMENT '会话ID',
    user_id BIGINT NOT NULL COMMENT '用户ID',
    agent_id BIGINT COMMENT 'Agent ID',
    message TEXT NOT NULL COMMENT '消息内容',
    role VARCHAR(20) NOT NULL COMMENT 'user/assistant',
    created_at TIMESTAMP DEFAULT CURRENT_TIMESTAMP,
    INDEX idx_conv_time (conversation_id, created_at),
    INDEX idx_user (user_id, created_at)
) COMMENT '对话历史记录';

-- 向量知识库（已有）
CREATE TABLE vector_store_openai (
    id UUID PRIMARY KEY DEFAULT gen_random_uuid(),
    content TEXT NOT NULL,
    metadata JSONB,
    embedding VECTOR(1536)
);
```

### Java 实现

```java
@Service
public class EnhancedMemoryService {

    @Autowired
    private MessageWindowChatMemory l1Memory;  // Spring AI

    @Autowired
    private ChatHistoryRepository l2Repository;  // MySQL

    @Autowired
    private PgVectorStore l3VectorStore;

    @Autowired
    private ChatModel chatModel;

    /**
     * 添加消息（每轮对话调用）
     */
    public void addMessage(String conversationId, Message msg) {
        // 1. 写入 L1（内存窗口）
        l1Memory.add(msg);

        // 2. 异步写入 L2（MySQL 持久化）
        CompletableFuture.runAsync(() ->
            l2Repository.save(new ChatHistory(conversationId, msg))
        );
    }

    /**
     * 重启后恢复上下文
     */
    @PostConstruct
    public void restoreContext(String conversationId) {
        List<Message> recent = l2Repository
            .findByConversationId(conversationId)
            .orderByDesc("created_at")
            .limit(20);  // 恢复最近20条到 L1

        recent.forEach(l1Memory::add);
    }

    /**
     * 会话结束后，筛选写入向量库（只调用一次 LLM）
     */
    public void onConversationEnd(String conversationId) {
        // 1. 从 MySQL 读取完整对话
        List<ChatHistory> fullConv = l2Repository
            .findByConversationId(conversationId);

        // 2. 规则快速过滤
        if (fullConv.size() < 5) return;  // 太短，无价值

        String text = fullConv.stream()
            .map(ChatHistory::getMessage)
            .collect(Collectors.joining("\n"));

        if (text.length() < 100) return;  // 内容太少

        // 3. LLM 提取结构化知识（只调用一次）
        String structured = extractKnowledge(fullConv);

        // 4. 写入向量库
        if (StringUtils.hasText(structured)) {
            l3VectorStore.add(List.of(Document.builder()
                .content(structured)
                .metadata(Map.of(
                    "conversation_id", conversationId,
                    "user_id", fullConv.get(0).getUserId(),
                    "created_at", LocalDateTime.now()
                ))
                .build()));
        }
    }

    /**
     * 提取可复用知识（保留关键细节）
     */
    private String extractKnowledge(List<ChatHistory> conversation) {
        String conversationText = conversation.stream()
            .map(c -> c.getRole() + ": " + c.getMessage())
            .collect(Collectors.joining("\n"));

        String prompt = """
            从以下对话中提取可复用的技术知识，要求：

            1. 过滤无效内容：
               - 去除"嗯、啊、好的、收到"等语气词
               - 去除纯闲聊内容

            2. 保留关键细节：
               - 所有表名、字段名、类名、方法名
               - 所有 SQL 语句、代码片段
               - 所有数字（数据量、参数值、版本号）
               - 所有决策和结论

            3. 结构化输出格式：
               ### 主题
               [一句话概括]

               ### 问题描述
               [用户遇到的具体问题]

               ### 解决方案
               [具体的技术方案，保留代码]

               ### 关键实体
               - 表名: xxx
               - 字段: xxx
               - SQL: ```sql ... ```

            4. 如果对话无明确技术价值，返回空字符串

            对话内容：
            {conversation}
            """;

        return chatModel.call(new Prompt(prompt,
            Map.of("conversation", conversationText)));
    }

    /**
     * 混合检索：时间序列 + 语义相似度
     */
    public List<Document> retrieveMemory(String userId, String query) {
        // 1. 精确查询：最近的对话（MySQL 时间排序）
        List<Message> recent = l2Repository
            .findByUserId(userId)
            .orderByDesc("created_at")
            .limit(10);

        // 2. 向量检索：相关的历史知识（语义相似度）
        List<Document> related = l3VectorStore.similaritySearch(
            SearchRequest.builder()
                .query(query)
                .filterExpression("user_id == " + userId)
                .topK(5)
                .build()
        );

        // 3. 合并：时间序列 + 相关知识
        List<Document> merged = new ArrayList<>();
        merged.addAll(recent.stream()
            .map(m -> new Document(m.getText()))
            .toList());
        merged.addAll(related);

        return merged;
    }
}
```

### 优化：异步批量筛选（降低成本）

```java
@Component
public class KnowledgeExtractionScheduler {

    @Autowired
    private ChatHistoryRepository chatRepository;

    @Autowired
    private PgVectorStore vectorStore;

    @Autowired
    private ChatModel chatModel;

    /**
     * 凌晨批量提取知识（避免阻塞用户对话）
     */
    @Scheduled(cron = "0 0 2 * * ?")  // 每天凌晨2点
    public void batchExtractKnowledge() {
        // 1. 查询昨天结束的会话
        LocalDate yesterday = LocalDate.now().minusDays(1);
        List<String> conversationIds = chatRepository
            .findEndedConversations(yesterday);

        // 2. 批量处理（减少 LLM 调用）
        List<Document> knowledgeDocs = new ArrayList<>();

        for (String convId : conversationIds) {
            List<ChatHistory> conv = chatRepository
                .findByConversationId(convId);

            // 规则过滤
            if (conv.size() < 5) continue;

            // LLM 提取知识
            String knowledge = extractKnowledge(conv);
            if (StringUtils.hasText(knowledge)) {
                knowledgeDocs.add(Document.builder()
                    .content(knowledge)
                    .metadata(Map.of("conversation_id", convId))
                    .build());
            }
        }

        // 3. 批量写入向量库
        if (!knowledgeDocs.isEmpty()) {
            vectorStore.add(knowledgeDocs);
            log.info("批量提取知识 {} 条", knowledgeDocs.size());
        }
    }
}
```

## 核心结论

### 好的实践

1. **必须有持久化层**：MySQL/PostgreSQL 存储完整对话历史
   - 重启恢复上下文
   - 按时间精确查询
   - 审计和追溯

2. **向量库用于知识检索**：不是对话历史存储
   - 语义相似度搜索
   - 跨会话知识复用
   - 需要精心筛选内容

3. **AI 筛选要异步**：不能阻塞每轮对话
   - 会话结束后批量处理
   - 凌晨定时任务
   - 规则预过滤 + LLM 精筛

4. **混合检索策略**：时间序列 + 语义相似度
   - 近期对话：MySQL 时间排序
   - 历史知识：向量语义检索
   - 两者结合提供完整上下文

### 需要避免的

1. **不要只依赖向量库**：无法精确按时间恢复上下文
2. **不要实时 AI 筛选**：成本高、延迟大
3. **不要过度总结**：会丢失关键细节（表名、SQL）
4. **不要用 MongoDB 存总结**：要存就存完整对话
5. **不要自己实现复杂记忆机制**：优先用 Spring AI 原生功能
